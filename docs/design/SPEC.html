WALL-E Drive — Phone Teleop UI

DESIGN BRIEF  ·  claude.ai/design source document  ·  Live source: pi_app/web/teleop.py _DRIVE_HTML

What Is This Screen?

A fail-safe phone teleoperation UI for WALL-E Mini, a 40 kg electric garden wagon with twin rubber tracks driven by two VESC motor controllers over CAN bus. The phone browser is the only human control surface during outdoor use. The operator holds the phone in one hand, typically in direct sunlight, possibly wearing work gloves, with the other hand free. The connection is plain Wi-Fi (LAN, no cloud path).

The UI is a dark, portrait-only, full-screen PWA (Add-to-Home-Screen on iOS/Android). All controls must be thumb-reachable in a single-handed grip. The visual hierarchy enforces safety priority: E-STOP is largest and most prominent, ARM is secondary, the joystick is the primary driving interface.

The server runs a 250 ms deadman watchdog. If the phone drops Wi-Fi or the browser tab hides, the robot stops automatically — the UI is a remote control for a real outdoor robot, not a game.

Arcade Mix Note

The UI presents a single 2D joystick to the operator. The client-side arcade mix converts (X, Y) axes into left/right tank track commands before sending over WebSocket:

throttle = -stickY   (stick up = forward = positive throttle)
left  = clamp(throttle + 0.8 × stickX, -1, 1)
right = clamp(throttle − 0.8 × stickX, -1, 1)

STEER_GAIN = 0.8 is a constant in the JS. The server then applies the active speed cap (0.3 / 0.6 / 1.0) server-side before writing motor bytes. Any redesign must preserve this client-side mixing — the server expects left/right track values, not X/Y joystick axes.

HARD CONSTRAINTS — Safety Affordances (Must Be Preserved)

These are not stylistic preferences. They exist because this is a real outdoor robot. Violating any of them in a redesign creates a safety regression.

  1. ARM requires a visible ~520ms hold affordance. The server enforces ≥500ms. The radial progress ring (or equivalent animated feedback) must clearly communicate to the operator that they must sustain a deliberate hold — accidental taps must not arm the robot.
  2. E-STOP must be the largest, most reachable control and must visually latch. It must be full-width (or the visual equivalent of maximum reachability), min 56px tall, always visible, and its latched state must be unambiguously distinct from idle (currently: inverted colour scheme + pulsing animation).
  3. The disconnect/deadman overlay must be full-screen, blocking, and require explicit dismissal. It must not auto-dismiss on reconnect alone — the operator must consciously acknowledge a deadman trip before being able to re-arm. Z-index must block all controls beneath it.
  4. All controls must be thumb-reachable in portrait one-handed operation with minimum 44px touch targets. The joystick pad, E-STOP, ARM, and speed control must all be reachable without repositioning the grip. The E-STOP must be reachable even with gloved hands / reduced dexterity.
  5. Pointer Events + spring-return behaviour must be preserved. The joystick uses pointerdown/pointermove/pointerup with setPointerCapture for correct multi-touch handling. The spring-return CSS transition (cubic-bezier(.34,1.56,.64,1), 220ms) is a safety feature: lifting the thumb stops the robot. E-STOP fires on pointerdown (not click) for minimum latency.
  6. State must remain legible in direct sunlight (contrast budget). The dark theme is intentional for outdoor use — an OLED/dark-mode phone in sunlight has better contrast than a washed-out light background. Any restyle must maintain sufficient contrast ratios: active/armed states vs. idle states must be distinguishable at arm's length in bright sunlight. The red E-STOP must remain immediately identifiable.

Restyle Guidance

The current baseline is functional but visually minimal. A restyle may: change the colour palette (preserving semantic colour roles: red=danger, green=armed/ok, blue=selected/active, amber=warn), improve typography hierarchy, update border-radius / shadow / glassmorphism style, add better iconography, or reflow the layout within the portrait phone form factor.

The restyle must be ported back into the _DRIVE_HTML inline string in pi_app/web/teleop.py. There is no build step — all CSS and JS must be inline. No external CDN dependencies. No frameworks. The file is served directly from a Flask Blueprint via return Response(_DRIVE_HTML, content_type="text/html").
